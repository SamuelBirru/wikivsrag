1 What the Repo Currently Is

This is a research prototype that compares two Q&A strategies over 100 ArXiv physics papers: RAG (vector search + generation) versus LLM Wiki (pre-synthesized concept pages + TF-IDF + generation). The core question it answers is: which pattern produces better physics answers?

Root Problem
The project works well for its stated goal. The problem is that it was built for abstract/full-text PDFs from ArXiv, not for LaTeX-heavy academic source material. The pipeline loses almost all mathematical structure before anything gets embedded.

3 How Ingestion Currently Works

ArXiv API → physics_papers.json (metadata) ↓ PDF download (requests → pdfs/*.pdf) ↓ PyMuPDF page.get_text() ← equations become "∂2ψ/∂x2" or mangled Unicode or just blank ↓ paper_texts.json ← flat string, no sections, no equation labels, no figure positions ↓ word-count chunker (400 words, 50 overlap) ← splits mid-equation, mid-theorem ↓ all-MiniLM-L6-v2 ← general-purpose English model, poor LaTeX domain knowledge ↓ FAISS IndexFlatIP ← stores 384-dim float32 vectors rag_chunks.pkl ← stores {text, meta: {id, title, url, chunk, total_chunks}}

What is lost at each step

  • page.get_text() — equation structure, subscript/superscript ordering, figure positions, table cells, caption text
  • word-count chunker — section boundaries, theorem/proof pairings, equation numbers and their surrounding prose
  • all-MiniLM-L6-v2 — mathematical semantics (no LaTeX training)
  • FAISS — no document hierarchy, no section metadata, no equation labels, no figure references

4 How Embeddings and FAISS Currently Work

Key Clarification
FAISS is a vector index, not an embedder. The embedding model (all-MiniLM-L6-v2) converts text to 384-dim float32 vectors — this is the step that "reads" meaning. FAISS stores those vectors and provides fast nearest-neighbor search. It never reads text; it only computes distances between float arrays. "Can FAISS store LaTeX embeddings?" means: after you embed LaTeX-preprocessed text through some model, FAISS stores those vectors just like any others. The index is format-agnostic.

Current FAISS setup

  • IndexFlatIP — exact inner-product search, no approximation. Fine for a few thousand chunks, scales to ~1M vectors before needing IndexIVFFlat or HNSW.
  • L2-normalized embeddings → inner product = cosine similarity
  • No metadata in FAISS — metadata lives in the parallel rag_chunks.pkl
  • No hierarchy — every chunk is a flat peer in the same index
Verdict
FAISS is not the bottleneck. The bottleneck is upstream: the embedding model and the quality of text fed into it.

5 What Breaks for LaTeX-Heavy Content

1. Equations

page.get_text() on a PDF equation like the wave equation produces something like ∂2ψ ∂x2 = 1 v2 ∂2ψ ∂t2 — direction/ordering often wrong, missing formatting. A query for "wave equation" or "equation 4" cannot locate it semantically.

2. Equation Numbers

"(4)" in a PDF is just a parenthesized number. The chunker separates it from the equation it labels. Queries like "equation 4" have no path to the right chunk.

3. Figures

PyMuPDF's page.get_text() does not return image bytes or alt text. Figures simply disappear. Captions sometimes survive but are severed from their figure.

4. Tables

Multi-column PDF table cells are linearized in reading order — often producing nonsense row ordering.

5. Section Hierarchy

page.get_text() returns a flat string. "Section 3.2 — Renormalization" becomes just more text. The chunker does not know where section boundaries are.

6. Bibliography

\cite{key} becomes a bare [12] in the PDF text. Citation keys are lost. Cross-referencing is impossible.

0. ArXiv Source Fetching — New Script Required

Gap in Current Code
The existing PhysicsScript.py --download flag only hits the PDF endpoint (paper["pdf_url"]). It has no knowledge of the ArXiv source endpoint. A new fetch function is required before any LaTeX-first ingestion can happen.

The Source Endpoint

ArXiv publishes raw source files at a separate HTTP endpoint — not surfaced by the metadata API:

https://arxiv.org/e-print/{arxiv_id}

The arxiv Python library (already installed) exposes this as result.download_source() in v2.x, but you can also hit it directly with requests.get() — the same pattern already used for PDFs in PhysicsScript.py.

Three Cases the Fetcher Must Handle

Response typeHow to detectActionRouting
.tar.gz archive Content-Type: application/x-eprint-tar or magic bytes 1f 8b + tar header Extract with tarfile; locate main .tex file; collect images and .bib status: "tex" → LaTeX parser
Single gzipped .tex Content-Type: application/x-eprint or .gz containing plain text Decompress with gzip; write as main.tex status: "tex" → LaTeX parser
PDF-only source Content-Type: application/pdf or magic bytes 25 50 44 46 (%PDF) Save to pdfs/ — no .tex exists for this paper status: "pdf_only" → Datalab / Gemini OCR fallback

Identifying the Main .tex File

Multi-file projects can contain 10+ .tex files. The reliable detection order is:

  1. Scan all .tex files for one containing \begin{document} — there should be exactly one.
  2. If none found (rare malformed submission), fall back to a file named main.tex, paper.tex, or {arxiv_id}.tex.
  3. If still ambiguous, pick the largest .tex file by byte size and log a warning.

Once the entry point is identified, rename or record it as the canonical main.tex for that paper. The \input{}/\include{} resolver in parse_latex.py uses this as its root.

Output: sources/ Directory + source_index.json

The fetcher writes a structured directory per paper and a routing index:

sources/
  2605.05537v1/
    main.tex
    sections/
      intro.tex
      methods.tex
    figures/
      fig1.pdf
      fig2.png
    bibliography.bib
  2605.05538v1/
    (pdf_only — no .tex extracted)

And a companion source_index.json that the ingestion pipeline reads to route each paper:

{
  "2605.05537v1": {
    "status": "tex",
    "main_tex": "sources/2605.05537v1/main.tex",
    "bib_file": "sources/2605.05537v1/bibliography.bib",
    "image_files": [
      "sources/2605.05537v1/figures/fig1.pdf",
      "sources/2605.05537v1/figures/fig2.png"
    ]
  },
  "2605.05538v1": {
    "status": "pdf_only",
    "main_tex": null,
    "pdf_fallback": "pdfs/2605.05538v1.pdf"
  }
}

Rate Limiting

ArXiv's bulk access policy requires a delay between requests on the source endpoint — the same constraint as PDF downloads. The existing DOWNLOAD_DELAY = 4 constant in PhysicsScript.py already satisfies this and should carry over unchanged. Do not parallelize requests; ArXiv will temporarily block the IP.

Where This Lives in the Codebase

Add a --download-source flag to PhysicsScript.py, parallel to the existing --download flag. Internally it calls a new function fetch_source() in the same file or extracted to ingest/fetch_source.py if you prefer the module layout. Either works — the important thing is that it runs before the ingestion pipeline and produces source_index.json that every downstream step reads.

A. LaTeX-First Ingestion

Where it plugs in
Replaces PhysicsScript.py's download_and_extract() and the _split_into_chunks() function in rag_system.py. New module: ingest/parse_latex.py

Recommended libraries: pylatexenc or plasTeX to parse .tex source to a structured tree without running a LaTeX compiler. A regex/state-machine approach on raw .tex text is practical for a prototype.

  • Detect entry point — find the .tex file containing \begin{document}
  • Recursively resolve \input{} and \include{}
  • Walk the parse tree extracting: section hierarchy, equations with labels, theorems/definitions/proofs, figures with captions, tables, citations

Metadata per chunk:

{
  "source_file": "main.tex",
  "source_line": 342,
  "section_path": ["2. Methods", "2.3 Hamiltonian"],
  "chunk_type": "equation",
  "latex_raw": "\\begin{equation}\n H = \\sum_i ...\n\\end{equation}",
  "label": "eq:hamiltonian",
  "equation_number": "3",
  "caption": null
}

B. PDF / OCR Fallback

Used when no .tex file is available.

Option 1 — Datalab (recommended)

Datalab's document parser outputs structured Markdown or JSON with section headers preserved, equations converted to LaTeX, tables reconstructed, and figure bounding boxes with captions. This is significantly better than raw PyMuPDF for academic papers. The output slots directly into the same metadata schema as the LaTeX parser.

Option 2 — Gemini 2.0 Flash (vision fallback)

For pages where OCR fails or figure-heavy documents, pass each PDF page as an image to Gemini: "Extract all text, equations (as LaTeX), table content, figure captions, and describe any figures on this page. Return structured JSON."

Practical Recommendation
Try Datalab first. If it handles equations and tables well, reserve Gemini for image description only. Gemini is more flexible but more expensive per page.

C. Embedding Strategy

Current Model Problem
all-MiniLM-L6-v2 is a general English sentence model with no scientific paper training. It may fail to recognize that H = Σ_i ε_i a†_i a_i is "the Hamiltonian of the system." For a physics wiki this matters.

Recommended replacement: allenai/specter2_base — trained specifically on scientific paper abstracts and citation relationships. Drop-in replacement for SentenceTransformer. Dimension is 768 instead of 384, so rebuild the FAISS index.

Chunk TypeBoundaryHow to Embed
Paragraph proseSentence-level, ~300 wordsClean text
Equation blockOne equation = one chunkRaw LaTeX + surrounding prose sentence
Theorem / ProofTheorem + proof = one chunkKeep together
FigureCaption + generated description = one chunkText only
TableCaption + table text = one chunkLinearize rows
Bibliography entryOne entry = one chunkBibTeX text

Hierarchical Retrieval

FAISS does not do hierarchy — it only does nearest-neighbor over flat vectors. Store parent-child relationships in your metadata store outside FAISS:

Document → Section → Subsection → Chunk

At query time: search FAISS for top-k matching chunks → look up each hit's section in the metadata store → optionally search at section level separately → re-rank combining both. This is sometimes called parent document retrieval: retrieve the chunk for scoring, expand context to the full parent section before sending to the LLM.

D. Image / Figure Handling

For each extracted image, pass to Gemini (or Claude with vision) with a physics-aware prompt. Store:

{
  "chunk_type": "figure",
  "image_path": "figures/fig3.png",
  "label": "fig:phase_diagram",
  "figure_number": "3",
  "original_caption": "Phase diagram of the Kitaev model...",
  "generated_description": "A 2D plot with axes J/K and h/K showing...",
  "surrounding_text": "As shown in Figure 3, the topological phase...",
  "section_path": ["3. Results", "3.1 Phase Structure"]
}

Embed original_caption + generated_description + surrounding_text as a single chunk.

Exact Query Shortcut
Queries like "equation 4" or "figure 2" should bypass semantic search entirely. Before running FAISS, check if the query matches a label pattern (eq:\w+, equation \d+, fig:\d+). If yes, do a direct metadata lookup — O(1) and always correct.

E. Bibliography Handling

ScenarioStrategy
Small .bib (< 500 entries) Parse and embed every entry using pybtex or a simple regex parser. Each entry = one chunk of type "bibliography".
Large .bib (500+ entries) Run pdflatex or latexmk to produce a .bbl file. Parse .bbl — only cited references are included. Embed only those.

When parsing LaTeX, record which cite keys appear in which chunk. Store cross-references in the metadata store. Queries like "what does the paper cite when discussing decoherence" then become answerable.

G. Claude Skill for Physics Wiki Creation

Skill name: physics-wiki-create

Description:
Given one or more LaTeX source files or a PDF, ingests the content into a structured physics knowledge base and produces a browsable wiki with definitions, equations, diagrams, references, and explanations.

Inputs:
source_path · bib_path (optional) · output_dir · ocr_mode: datalab|gemini|none · embed_model: specter2|minilm

Ingestion workflow:
1. Detect source type (tex / pdf / dir)
2. If .tex → LaTeX parser → structured chunks
3. If .pdf → Datalab OCR or Gemini page-by-page
4. Extract images → vision description
5. Parse .bib or compile .bbl → bibliography chunks
6. Embed all chunks with SPECTER2
7. Build FAISS index + metadata store

Wiki generation:
8. Group chunks by section hierarchy
9. Claude synthesizes one wiki page per section
10. Preserve raw LaTeX in equation blocks
11. Include figure descriptions + captions
12. Write markdown to output_dir with _index.json

Retrieval workflow:
13. Check for label/number pattern → metadata lookup (O(1))
14. Otherwise → embed query → FAISS search
15. Expand to parent section context
16. MMR re-rank → Claude generates answer

Quality checks:
Verify equation count · verify \label{} references resolve · flag figures missing descriptions · warn on large .bib without .bbl

Failure modes:
Nested \input{} loops · malformed .tex · image description API timeout · scanned PDF with no text

7 Should You Keep FAISS?

Short-term (prototype)
Keep FAISS
Medium-term (structured queries)
Augment with metadata store
Long-term (production / multi-user)
Migrate to pgvector

Keep FAISS for the prototype because it already works, is CPU-only with no infrastructure, uses exact search, and is fine for up to ~100K chunks. The real improvements are upstream of FAISS: better text (LaTeX parser or Datalab) and a better embedding model (SPECTER2).

When to Replace

  • Multi-user / always-on deployment → pgvector on RDS (combines metadata queries with vector search in SQL)
  • Need to filter by chunk_type before search → pgvector handles this natively; FAISS requires post-filtering
  • Incremental updates → FAISS requires full index rebuild; pgvector supports INSERT

11 One Honest Uncertainty

Datalab Accuracy on Real Physics Papers

Datalab's documentation advertises structured Markdown/JSON output with LaTeX equation conversion for scientific PDFs, but real-world accuracy on complex physics papers — dense notation, custom macros, multi-column layouts — may vary.

Before committing to Datalab as the OCR fallback, test it on 3–5 representative papers from your corpus and manually inspect the equation extraction. Gemini 2.0 Flash is a known-good alternative that is more flexible (you can prompt it precisely) but costs more per page.
